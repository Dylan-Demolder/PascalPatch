# Static plugin composition

The first code-plugin path is source composition, not runtime relocatable loading. `tooling/build_static_plugin.py` uses the pinned tools from the decompilation checkout when available and creates a disposable Git worktree, generates one bundle source, includes that bundle into the linked `gmmain.c` unit, builds a GALE01 DOL and copies only the generated DOL to the requested output. The original checkout and extracted game tree are not modified.

Each plugin manifest must provide a C-identifier `entrypoint` and a relative `.c` `source`. Plugin source must use the target GameCube ABI. This is an explicit build-time code execution boundary; install only code you trust.

The adapter was validated with a harmless `OSReport` plugin. A generated marker was present in the output DOL. The real hello-plugin and PPC-safe runtime ABI also compile and link; its log string is present in the DOL. Plugin initialization defaults to the first game-loop frame, after startup services are ready. An explicit `init_phase: startup` is available for trusted diagnostics and has been observed in standalone Dolphin: `[meleemod] hello-plugin initialized` appears in OSREPORT. The first-party startup probe also observes `[meleemod] startup-probe runtime-ready observed` after subscribing to `MM_EVENT_RUNTIME_READY`. The clean, static, and recomposed runtime-plugin ISOs boot to the same Melee memory-card prompt in standalone Dolphin 2606. Default first-frame callback output, shutdown ordering and dynamic modules remain separate work.
